# V2 Data Model

The V2 architecture introduces a structured data model to support asynchronous command processing, operation tracking, and idempotency.

Two main logical entities are required:

- key-value data
- operations tracking

---

# 1. Key Value Store

This table stores the current value associated with each key.

It represents the persistent state of the system.

## Table: key_value_store

Fields:

- key (PRIMARY KEY)
- value
- updated_at

### Description

key  
Unique identifier of the stored value.

value  
The stored data associated with the key.

updated_at  
Timestamp of the last successful modification.

### Notes

- Redis acts as a cache layer for fast reads.
- CockroachDB is the source of truth for the stored data.
- Cache entries may be invalidated or refreshed after write operations.

---

# 2. Operations

This table tracks asynchronous commands submitted by clients.

It allows clients to monitor the progress of operations and ensures better observability of the system.

## Table: operations

Fields:

- operation_id (PRIMARY KEY)
- request_id
- operation_type
- key
- value
- status
- retry_count
- error_message
- created_at
- updated_at

---

## Field descriptions

operation_id  
Unique identifier of the operation generated by the API.

request_id  
Identifier used for request tracing across services.

operation_type  
Type of operation requested.

Possible values:
- PUT
- DELETE

key  
The key affected by the operation.

value  
Value associated with the operation (only for PUT).

status  
Current state of the operation.

Possible values:

- ACCEPTED
- PROCESSING
- COMPLETED
- FAILED
- DEAD_LETTERED

retry_count  
Number of retry attempts performed by workers.

error_message  
Optional error description if the operation fails.

created_at  
Timestamp when the operation was accepted by the API.

updated_at  
Timestamp of the last state change.

---

# 3. Operation Lifecycle

Operations move through several states during their lifecycle.

ACCEPTED  
The API received the command and stored the operation.

PROCESSING  
A worker is currently executing the operation.

COMPLETED  
The operation finished successfully.

FAILED  
The operation failed but may still be retried.

DEAD_LETTERED  
The operation exceeded the retry limit and was moved to a dead-letter queue.

---

# 4. Idempotency Strategy

To prevent duplicate processing, the system uses operation_id to track executed commands.

Before executing a command, workers must verify the operation status.

If an operation is already marked as COMPLETED, the command must not be executed again.

This prevents duplicate writes caused by message redelivery or retries.

---

# 5. Relationship Between Operations and Data

Operations modify the key_value_store.

Example workflow:

1. Client submits PUT command
2. API creates operation record
3. Worker processes message
4. Worker updates key_value_store
5. Worker marks operation as COMPLETED
